# 1delta-x core — independent audit & architecture assessment (2026-09-17)

Scope: `packages/core/src` (settlement + permit3 + utils, ~5,900 SLOC), the module
interfaces it dispatches, and a representative lending module. Method: full-file
read of every in-scope contract, plus Slither 0.11.6 and Semgrep 1.177.0 (Decurity
Solidity ruleset), plus a spec-to-code pass against the repo's own design notes.

## 1. Security verdict

**No new Critical, High, or Medium security findings.** The codebase is the most
thoroughly self-audited Solidity tree in its class — it carries a nine-round on-disk
ledger (F1–F29), a fifteen-class failure corpus (C1–C15) distilled from the
published 1inch/0x/CoW/UniswapX exploits, and a bounty corpus (B1–B14). The one
divergence this pass produced is a **documentation drift**, not a code defect.

The architecture is **coherent, layered, and unusually well-reasoned**. Its single
dominant risk is a physical constraint, not a design flaw: Settlement sits at
~24,476 / 24,576 bytes of EIP-170, so the whole system is shaped by a bytecode
budget it has largely exhausted.

## 3. Findings

### 3.1 Documentation drift (only finding — low, no security impact)

`docs/deferred-match-settle.md` is internally contradictory about what `_stepPull`
credits to the match ledger. §5.1 and §13.4(2) claim a **measured** balance delta;
§9.1(2) and the shipped `Batch._stepPull` credit the **nominal `owed`** (`need =
owed − have`, no `balanceOf` around the pull). Both shapes fail closed (measured →
`LegUnfunded`; nominal → `BatchNotWhole`); the nominal form just gives a less precise
error and makes fee-on-transfer inputs out of scope on the netted path. The §5.1/§13.4
"measured" notes are stale. **Fix the doc, not the code.**

### 3.2 Verified properties (fresh trace, not comment-trust)

- **C1 (arbitrary call from the settler) closed** — callbacks and `matchSettle` `CALL`
  steps run through `SolverCallbackExecutor`, an allowance-less, Settlement-pinned
  trampoline; item dispatch is selector-pinned (`Base._callWithTail`).
- **C5 (maker-supplied price) closed** — `IPriceModule` returns a clamped shared
  bump; `IFillModule` returns only a `delta`, capped by `filled + delta ≤ total`.
  Both `view`.
- **C6 (overfill) closed in two layers** — `_gateFillState` rejects `prevFilled ≥
  total` first; `_openFill` keeps the universal `newFilled > total` cap.
- **`fillWithPermitTake` authorization is a pre-condition** of the input pull
  (`PermitTakeNotConsumed` fires after items, before the wallet pull).
- **`matchSettle` exactly-once guards** (`PlanBadStep`) sit set-and-check at the step
  (S8), not as a post-hoc completeness compare.
- **`OrderHash.hash`** — all 16 preimage words traced against the typehash field
  order and the four address masks; correct.
- **Nonce namespacing** — `SIGNER_NONCE_NS` (bit 255) enforced on both halves.
- **F29 #5/#7 fixes correct** — the `type(uint256).max` `matchSettle` sentinel and the
  refused-lapsed-nomination change are sound.
- **No native-token surface** — zero `payable`/`msg.value`/`0xEeee` in scope.

### 3.3 Injection surface (malicious modules / filler / callbacks)

- **Malicious maker modules are self-scoped.** A module is reached only as a
  maker-signed field, and no dispatch forwards Settlement's Permit3-spender status to
  it. MAKE/TAKE/TAKE_FOR/SETTLE all pin `msg.sender`; the pool grants no approvals;
  `take`/`takeFor` are `nonReentrant`. A malicious module can only harm its own maker.
- **Filler-injected callbacks and `takerData` cannot move maker funds.** `fillWithCallback`
  and `CALL` steps run through the allowance-less EXECUTOR; `takerData` reaches only
  `view`/`STATICCALL` gates and is never interpreted by the core.
- **`pricingModule`/`fillModule`** are maker-signed, `view`, and bounded.

## 4. Architecture — Permit3

Two allowance books, keyed by spender: the token book (`AllowanceTransfer`,
Permit2-equivalent) and the **taker book** (`TakerAllowance`, no Permit2 analogue)
for operations that don't fit `transferFrom` (borrow/withdraw/claim). Authority is
granted three ways: on-chain (`approveToken`/`approveTaker`), signed batch
(`permitBatch(…WithWitness)` — binds the grant to the order hash), and one-shot
(`permitTransferFrom`/`permitTake`).

**What is right.** `module` is part of the taker key (S-2) — the single most
important Permit3 decision, since minimal `data` layouts mean distinct modules
routinely share a `ref`; naming the module in the key makes a borrow grant unusable
to dispatch any other module. Witness permits close the C11 permit-as-liveness-bomb
class (the `…IfNeeded` idempotent path). The packed allowance slot is one
SLOAD/SSTORE; `expiration == 0` means never-expires; `type(uint160).max` never
decrements.

**Flags.** Permit-nonce namespacing is *off-chain-only* (SDK) — the opposite of the
order nonce's on-chain `SIGNER_NONCE_NS` — so a hand-rolled client can still collide
permit kinds. And `transferFrom` is deliberately un-locked with a direct-approval
fallback, so "revoke Permit3" is not a kill switch (strict mode is the opt-in).

## 5. Architecture — Settlement

Seven single-responsibility layers (`NonceManager → OrderState → Signatures → Base →
Core → Batch → Settlement`) over two execution paths: the single-order hot path
(`Core`) and the netted match (`Batch.matchSettle`).

**What is right.** The **memory-context insight** is the best decision in the tree:
`matchSettle`'s deferred context is one `MatchCtx` struct in memory, never crossing a
call boundary — because participants are known at call time, the EVC transient-storage
problem doesn't exist here, so `nonReentrant` stays unweakened and sufficient. The
packed `bytes` blob encoding collapses EIP-712's per-element hashing (struct hash
4,321 → 1,874 gas; leg read 744 → 379). The `FillCtx` receipts/outs ledger records
what was priced (~40 gas vs 795–3,583 to re-price) and is also a correctness device
(a ledger can't be double-spent).

**The flag — the bytecode wall is the architecture's ceiling.** ~24,476/24,576 bytes,
`optimizer_runs = 100` on the deploy profile. via-IR is required; the codegen is
cliff-dominated and non-monotonic (the same transform measured +1,862 bytes in one
tree and −65 in another; deleting code made it *bigger*); the gas/bytecode trade the
dial buys is invisible to the committed baseline. Every future feature is a
bytecode-cliff decision, and the address is a CREATE2 hash of initcode — any change
is a deployment-family migration.

## 6. Architecture — modules

Protocol heterogeneity lives in single-operation modules (`MAKE`/`TAKE`/`SETTLE`/
`TAKE_FOR`), dispatched by Settlement (MAKE/SETTLE) or Permit3 (TAKE/TAKE_FOR). The
core never decodes module `data`.

**What is right.** Blast radius is the grant, not the contract ("merge by grant, not
by venue"). The **invariant → measurement matrix** (`docs/module-security-model.md`,
I-1…I-16) maps every invariant to *which* mechanical check carries it —
`tools/check-module-shapes.py` (syntactic, CI), a named test, a `make` gate, or
(explicitly a gap) "prose only" — the direct countermeasure to the "rule re-typed per
call site eventually misses a site" failure mode. The **fake-module argument** is
load-bearing: *a fake module can fake a call but not a balance* — proceeds are
measured, delivery is a real transfer, and `PlanIncomplete`/`LegUnfunded`/`BatchNotWhole`
make input and output inseparable, which is what makes a no-whitelist module set safe.

**Flags.** Module safety rests on two deployment assumptions ([A1] no FoT/rebasing
reserve, [A2] no persistent module balance), not enforceable invariants — and the F-3
residue class has resurfaced across three rounds. The shapes checker is syntactic
(call-site level, not a proof).

## 7. Efficiency & maturity

The wins are real and measured: packed encoding, warm-slot nonce invalidator (~2,900
vs 22,100), hand-encoded `_permitBatch` (−297 bytes, −590…1,660 gas), hand-encoded
item dispatch (−65 bytes). But efficiency has become a **size game**: nearly every
assembly block saves bytes (EIP-170), not gas, and the size game is nearly lost. The
hand-rolled assembly is argued in comments, not enforced by the compiler, and each
change is a re-measure job. The measurement discipline (record *how* each number was
measured and on which profile) is the real asset — it caught its own warm-cache
figures running ~110 bytes low.

**Maturity scorecard (9 categories):** Arithmetic, Auditing, Access control,
Decentralization, Documentation, MEV, Testing — all **Strong**; Complexity and
Low-level manipulation — **Moderate** (both caused by the bytecode wall).

## 8. Exotic settlements (NFTs) vs matching

**Matching is correctly closed to non-fungible assets.** NFTs settle via the
filler-aware `SETTLE` op; `matchSettle` rejects `SETTLE`/`TAKE_FOR`/pre-fund MAKE at
open (`MatchSettleItemUnsupported`), legs are ERC20-only (`safeTransfer` uses
`transfer(address,uint256)`), and the measured-delta accounting cannot be faked by a
non-fungible "balance". A `fillModule` order can be matched but cannot move an NFT
(`resolveFill` is `view`; the hand-off needs a SETTLE item, which is rejected).

The genuine exposure is **single-order, not matching**: the filler-side receipt in a
`SETTLE` order is not on-chain guaranteed — a hostile maker can sign an "NFT sale"
whose module is a no-op, take the `tokenOut` payment, and deliver nothing. Mitigation
is documented and off-chain (vet the `(module, collection, tokenId)` triple; wrap the
fill to assert post-state; simulation is insufficient). This asymmetry is exactly why
`SETTLE` was kept out of the netted path.

## 9. Generic execution intents ("pay for X" / "receive for Y")

Both are structurally bounded. There is **no "execute arbitrary call" primitive**:
execution is the maker's signed module (scoped to their position) or the filler's own
allowance-less callback.

- **"Pay for operation X"** (reward harvest) = outputless SELL + rising fee leg. The
  operation is maker-scoped (signed module, `msg.sender`-pinned), the fee is
  auction-bounded to the signed ceiling `FMAX`.
- **"Receive USDC for operation Y"** = TAKE the result + inline sell. The
  deliver→items→pay ordering makes the payment contingent on the work funding the
  input (a faked harvest credits zero → `LegUnfunded`), and the amount is signed or
  measured, never "whatever the module reports".

The one unbounded thing is the **standing venue grant** the module must hold to do the
work — maker-side key management, not a core defect.

## 10. Lending modules — the allowance constellation

Four grant layers:

| Layer | Holder | Bound |
|---|---|---|
| ERC20 `approve(Permit3, max)` | Permit3 (hub) | infinite |
| Permit3 **token** allowance | module | amount + expiry |
| Permit3 **taker** allowance | Settlement | amount + expiry, keyed `(module, ref)` |
| **Venue-native grant** (delegation/operator/allow) | module | **standing, `max`** |

"**Infinite-approve Permit3" does not mean "infinite-approve every module"** — it
means one broad grant to a trusted hub that re-issues narrow, per-operation caps. The
token and taker books are amount-gated and non-overexposing. Borrowing is the explicit
exception: it needs a protocol-native grant (`approveDelegation(module, max)`) that is
standing, amount-unbounded, and Permit3-uncancellable.

That overexposure is contained by the pinned-entrypoint discipline: `takeOnBehalf`
reverts unless `msg.sender == permit3`, and no other function reaches `pool.borrow`,
so a correct module can only borrow inside the taker-allowance-gated dispatch; the
`ref` keying (op inside `data`) prevents a `Borrow` grant replaying as `Leverage`; and
an optional per-order `delegationWithSig` leaves nothing behind. **The residual: a bug
in a credit-delegation module is a standing, uncapped drain** — which is why the
I-invariants and `check-module-shapes.py` are mandatory for exactly these modules.

Reading `AaveV3CreditModule` line-by-line confirmed the implementation answers six
distinct prior findings: `msg.sender == permit3` + `requireSettlement(spender)`
(F27/C-1), the data-space split (F23), `Narrow160.to160` (F-2 drain), measured payout
+ cap + excess-to-maker (H-3/River), scoped approve+clear (A-3), residue floor+sweep
(I-6/I-7), and `revert BadOp` (the grant-merge basis).

## 12. Test setup & coverage quality

**The setup.** ~830 test functions in core across ~60 files (`swaps/`, `items/`,
`permit3/`, `utils/`, `invariants/`), plus per-module and fork suites. The crown
jewel is the **stateful invariant fuzz** (`StateHandler` + `CoreStateInvariants`):
a closed world (3 makers, 2 fillers, 1 attacker) snapshot-diffing 69 (now 81) watched state
cells against an allowlist, so any write to a cell its caller had no authority over
surfaces as an *unallowed diff* — a negative property over the whole authority
model, not an enumerated scenario. On top of it: the **golden-hash cross-check**
(`EncodingGolden.t.sol` ↔ SDK fixture ↔ `HashGolden.t.sol`), the **edge-case
matrix** (`docs/edge-case-matrix.md`, every revert a must-not cell naming its
pinning test), and the `gas`/`size`/`modules`/`docs` Makefile gates.

**What is strong.** Negative-property testing; coverage as a first-class artifact
(the matrix's own rule — *"a test that cannot fail is a coverage claim without
coverage"*); `fail_on_revert=false` handled by recording findings into per-family
strings rather than asserting inline, so a swallowed revert cannot turn a broken
contract green.

**Findings (wiring, not artifacts).** (1) `[profile.core.invariant]` — with the
`fail_on_revert=false` foundry.toml calls *required* — had **no dedicated Makefile
target and no CI job**. (It did activate under `make test PKG=core`, which runs the
`core` profile; what was missing was a scoped target and a gate, not the setting.) (2) The only CI was `gas.yml` (`make gas-check`); the
module packages' tests, `modules-check`, `docs-check`, `test-fork` and `test-ts`
were not CI-gated. (3) Accepted-but-real gaps recorded in the matrix: EIP-1271
makers untested through non-`fill` entry points (R-1), block-clock × partial fills
untested (R-2), the EVC mutual-leverage fork test outstanding. (4) No line/branch
coverage signal — the repo tracks behavior + invariant coverage, not `forge
coverage`.

**Action taken this run.** Added `make test-invariant`
(`FOUNDRY_PROFILE=core forge test --match-path "packages/core/test/invariants/*"`)
and `.github/workflows/test.yml`, which CI-gates `test-invariant`, `modules-check`,
and `docs-check`. Two subtleties surfaced while wiring it: `[profile.core.invariant]`
is the `core` profile's `invariant` *section*, not a separate profile (invoking it
as `core.invariant` resolves a fresh profile inheriting `default`'s whole-monorepo
`src`, which pulls every module in and fails on the bridge module's stack-too-deep),
and `--match-path` needs the trailing `/*` glob. Verified: `modules-check` (31 taker
+ 65 maker contracts scanned), `docs-check` (1,786 test functions, 38 docs — all
citations resolve), and the invariant suite compiles and passes (25 tests: 16
StateAuthFuzz + 9 CoreStateInvariants) under its profile. `test-all`/`test-fork`/
`test-ts` remain manual (RPC and node-install dependencies deliberately kept out of
the fast gate).
